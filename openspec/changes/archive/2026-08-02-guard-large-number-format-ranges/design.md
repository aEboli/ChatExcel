## Context

Office.js 将 `Range.numberFormat` 定义为二维数组。任务窗格已经允许整列和整行 A1 地址，但数字格式执行器在读取范围元数据后，会为每个单元格创建一个格式代码。该方式对普通矩形范围可行，对整列或整行会放大为工作表的实际行列数。

## Goals / Non-Goals

**Goals:**

- 在任何数字格式二维数组分配前，以 Office.js 返回的实际范围尺寸执行上限检查。
- 用与批量写入一致的 5,000 单元格预算限制单次数字格式操作，并向 Agent 返回可恢复错误。
- 保持整列、整行地址对不需二维矩阵的工具可用。

**Non-Goals:**

- 不实现隐式分块、后台多次修改或绕过用户的单次审批语义。
- 不改变 `format_range`、`autofit_range`、读取上限、网络协议或原生 `.xls` 路径。
- 不尝试向 `Range.numberFormat` 写入 Office.js 未定义的标量格式值。

## Decisions

### 在执行器元数据阶段拒绝超限范围

新增 `MAX_NUMBER_FORMAT_CELLS`，值与现有 `MAX_WRITE_CELLS` 相同，为 5,000。执行器在 `loadRangeMetadata` 后计算 `rowCount * columnCount`，超过上限即抛出 `NUMBER_FORMAT_RANGE_TOO_LARGE`，然后才可能构造 `numberFormat` 二维矩阵。

把检查放在共享 Schema 之外，因为 A1 地址不能可靠反映工作表的实际行列数。把它放在赋值之后也不能避免内存分配。该错误会经过现有工具错误结果和 Agent 恢复循环，使模型可以缩小或分块重试。

### 不在执行器中自动分块

自动分块会将一次审批变成多个工作簿修改，并在中途失败时留下部分格式；这与当前失败关闭和操作审计语义不符。由 Agent 根据结构化错误发起下一次、可审计的较小范围调用。

### 保留二维数组赋值

官方 Office.js 文档将 `Range.numberFormat` 定义为 `any[][]`。继续为已验证的小范围生成矩阵，避免引入未定义的标量赋值行为。

## Risks / Trade-offs

- [用户请求整列数字格式会被拒绝] -> 返回实际单元格数和上限，指导 Agent 缩小或分块。
- [5,000 个单元格仍需要内存] -> 与现有批量写入预算一致，且远低于整列/整行规模。
- [元数据同步失败] -> 在任何格式写入前失败，并沿用现有结构化 Office 错误处理。

## Migration Plan

无需迁移数据或配置。部署后，超限数字格式请求不再触发大数组分配；调用方收到可恢复错误后可提交较小范围。回滚只需恢复原执行器，但会重新引入内存风险。
