## Context

`scripts/start.ps1` 当前直接启动 `node src/server/index.js`，完成一次健康检查后退出。Excel 在本地任务窗格 URL 无法加载时显示宿主错误页，因而前端不能在用户点击“重试”时自行执行启动逻辑。现有启动器复用该脚本，所以同一缺口同时影响开发流程和 Windows 发行版。

## Goals / Non-Goals

**Goals:**

- 在 ChatExcel 已经由项目启动后，自动恢复项目受管的 Node.js 服务。
- 让服务恢复遵循现有 HTTPS 健康检查、回环地址和项目 PID 所有权检查。
- 让显式停止可靠地终止守护与服务，避免用户停止后被后台重新拉起。
- 保持启动器、开发脚本和发行目录使用同一条恢复路径。

**Non-Goals:**

- 不尝试从 Excel 宿主的离线错误页直接执行 JavaScript 或任意本地命令。
- 不安装 Windows 服务、计划任务、开机自启项或常驻跨会话代理。
- 不接管、停止或复用占用 `3210` 端口的非本项目进程。
- 不改变 HTTP API、模型配置、DPAPI 密钥保护或模型令牌边界。

## Decisions

### 用项目启动的后台守护器恢复服务

`start.ps1` 在正常启动或复用服务时确保一个隐藏的 PowerShell 守护器存在。守护器只负责运行项目固定的 `node src/server/index.js`，轮询既有 `/api/health`，并在受管 Node 进程退出或健康检查未恢复时重新启动它。这样不需要修改无法加载时根本不会执行的任务窗格代码。

前端重试和 Windows 服务都不采用：前者无法跨越宿主离线页，后者需要额外安装、权限与跨会话生命周期。守护器仅在用户已经使用 ChatExcel 启动流程后存在，范围更小。

### 用受项目目录限制的 PID 与停止信号管理所有权

`.runtime/service.pid` 继续标识 Node 服务，新增守护 PID 与停止信号文件。守护器仅在 PID 指向 Node 进程且该 PID 实际监听项目端口时终止或替换它；端口由其他 PID 占用时只记录可诊断状态并等待，不进行进程控制。

显式 `stop:local` 先发送停止信号并停止受管守护器，再按现有端口/PID 校验停止 Node 服务，最后清理运行时标记。这样不会因服务退出触发下一轮自动恢复。

### 使用健康检查和有界重试

守护器启动 Node 后等待已有 HTTPS 健康接口通过，启动期间给出短暂宽限；连续失败采用有限退避而不是紧密循环。它不读取模型配置或请求数据，诊断仅写入原有 `.runtime` 日志目录。

## Risks / Trade-offs

- [证书损坏或代码无法启动] -> 守护器会在有限退避后继续记录失败；用户仍可查看已有 stderr 日志并运行证书修复命令。
- [用户在服务恢复前立即点击一次宿主“重试”] -> Excel 可能仍显示一次失败；守护器完成健康检查后再次点击“重试”会重新加载，且恢复通常在短时间内完成。
- [外部程序占用项目端口] -> 守护器不终止该程序，启动流程保留明确端口冲突错误。
- [守护器意外终止] -> 已健康的 Node 服务继续可用；下一次 `start:local` 或 Launcher 启动会重新建立守护器。

## Migration Plan

部署新脚本后，下一次 `npm run start:local` 或 Launcher 启动会创建守护器，无需迁移配置或工作簿数据。回滚时先运行 `npm run stop:local`，再恢复旧脚本；用户的 Excel 文件、配置和加载项注册不受影响。
