## Context

ChatExcel 的共享工具 Schema 已限制读写矩阵和数字格式范围，但 Office.js 与原生 `.xls` 对范围格式、清除、排序、表格、图表和自动调整的实际影响面尚未采用同一策略。现有任务窗格拥有两种用户选择的审批模式：`required` 逐项确认，`auto` 先告知后直接执行。本次不能改变该选择、审批面板、设置持久化或串行工具循环。

OfficeCLI 的开源 XLSX 规则提供了可借鉴的预检、公式质量和交付验证原则，但它的命令行/OOXML 对象模型不能替换 ChatExcel 的 Office.js 和原生 `.xls` 执行器。

## Goals / Non-Goals

**Goals:**

- 在所有范围型修改执行前，根据 Excel 实际范围尺寸执行统一的影响面积检查。
- 允许低成本的整列/整行自动调整，同时限制一次自动调整涉及的实际行或列数量。
- 在成功同步后返回统一、可审计的 `verification` 摘要，并让模型根据公式错误或不匹配结果继续修复。
- 在 Office.js 和原生 `.xls` 路径使用相同的上限、结构化错误码和结果字段语义。
- 通过 Agent 指令落实公式优先、保留非目标内容、先读后改和完成前检查公式错误。

**Non-Goals:**

- 不改变 `required | auto` 的审批、告知、拒绝、设置持久化或任务窗格 UI 行为。
- 不新增数据验证、条件格式、冻结窗格、工作表保护或工作簿回滚工具。
- 不放宽连续 A1 地址、工作簿边界、只读保护、宏、VBA、Power Query 或 PivotTable 的现有约束。
- 不承诺对写后验证失败的工作簿进行通用回滚；Excel 已经成功写入时只返回失败而不伪造成功。

## Decisions

### 共享的影响限制按操作类型计算

在共享工具模块定义 `MAX_MUTATION_CELLS = 5_000` 和 `MAX_AUTOFIT_DIMENSIONS = 5_000`，并由两个引擎在实际获取范围尺寸后执行检查。

- 值、公式、范围格式、数字格式、清除、排序、创建表格和图表源范围使用 `rowCount * columnCount`，超限返回 `MODIFY_RANGE_TOO_LARGE`；数字格式保留既有兼容错误码 `NUMBER_FORMAT_RANGE_TOO_LARGE`。
- 自动调整不以整列/整行的理论单元格数计量：`columns=true` 限制目标列数，`rows=true` 限制目标行数。这样 `N:R` 自动调整列宽和 `1:3` 自动调整行高继续有效。
- 图表位置地址收紧为单个单元格或矩形，拒绝整行/整列位置，避免巨大或歧义的图表锚点。

替代方案是禁止所有整行/整列修改。该方案会破坏现有已规格化的自动调整工作流，因此不采用。

### 预检在执行器内完成，不改变审批流程

执行器在读取实际元数据后、写入前检查限制，并在安全范围内统计非空单元格、公式单元格和公式错误数量。预检信息作为工具结果的 `impact` 返回，供模型和活动记录审计。

不在审批弹窗前插入新的预检交互：这会改变 `required` 的原始参数确认时机，并可能把 `auto` 模式变成间接审批。用户现有模式只决定是否批准有效工具调用，安全上限对两种模式一视同仁。

### 写后验证是操作特定的轻量读回

修改同步后，执行器读取与操作相关的实际对象或范围并返回 `verification`：值/公式验证矩阵回读，数字格式验证格式矩阵，范围格式验证请求的格式属性，清除验证内容状态，排序验证关键列读回，表格和图表验证新对象标识。验证读取或对象确认失败时，工具返回结构化错误而不返回 `ok: true`。

验证不把公式错误自动当作执行失败，而是将错误计数写入结果并由 Agent 指令要求在任务完成前修复；这保留了分步搭建公式和后续补数据的工作流。

### 原生 `.xls` 对齐核心结果契约

原生执行器已在 Node 桥接层复用共享参数 Schema。C# 执行层增加相同的范围/自动调整检查，并将范围元数据和验证摘要返回到桥接响应。无法在不破坏 COM 兼容性的情况下完成的细粒度格式读取使用对象存在性或范围读回替代，且字段名称保持 `impact` / `verification` 一致。

### Agent 指令只表达质量目标，不取代执行器校验

在 `AGENT_INSTRUCTIONS` 中明确：在可计算时使用公式，先读取目标区域，避免覆盖非目标内容，完成前检查工具结果中的公式错误和验证摘要。范围限制、地址约束和成功判定仍由共享 Schema 与执行器强制，而不是依赖模型遵守提示词。

## Risks / Trade-offs

- [写后验证读取失败时 Excel 已完成修改] → 返回失败而不声称成功，附带目标信息，允许模型或用户读取确认；不执行不可靠的通用回滚。
- [读取预检增加 Office.js/COM 往返] → 仅对 `5,000` 单元格以内的范围读取必要属性，自动调整只读取尺寸。
- [整个行/列范围与既有规格冲突] → 按操作语义分别计算单元格或维度，保留安全的 `N:R`/`1:3` 自动调整案例。
- [公式错误可能是中间状态] → 报告错误计数并在完成前要求修复，不让单次公式写入机械失败。
- [原生 COM 与 Office.js 返回细节不同] → 共享错误码和顶层字段，测试各自实际可核验的摘要而不要求底层对象完全同构。

## Migration Plan

1. 在共享模块增加常量、地址限制和测试。
2. 在 Office.js 执行器增加预检、影响摘要和读回验证，补充模拟 Excel 测试。
3. 对原生 `.xls` 执行器增加相同范围检查和核心结果字段，构建 Launcher 与原生 smoke 测试。
4. 更新 Agent 指令和契约测试，确认审批模式测试仍覆盖 `required` 与 `auto` 的原有行为。
5. 运行 JavaScript 测试、语法检查、Launcher 构建与严格 OpenSpec 验证；真实 Excel 验收在现有活动变更的宿主验证任务中执行。
